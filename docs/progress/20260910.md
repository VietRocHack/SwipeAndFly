## 2026-09-10 - Remove Docker, split backend/frontend deploy

Executed the backlog item from the previous session (deferred then to
save session usage): dropped the single-container Docker architecture
entirely in favor of the migration guide's default topology. See ADR
0004 for the full decision record.

- Confirmed with Vuong that `swipeandfly.world` (the old VM deploy) is
  dead, which unblocked removing everything nginx-related.
- Removed: `Dockerfile`, `cloudbuild.yaml`, `docker-compose.yml`,
  `docker-compose.prod.yml`, `user_conf.d/`, `.dockerignore`,
  `scripts/deploy-prod.sh`, the placeholder top-level `public/` dir, and
  `backend/src/routes/frontend_routes.py` (Flask's static-file-serving
  catch-all, now redundant since Firebase Hosting serves the frontend
  directly).
- Backend now deploys as its own Cloud Run service straight from source
  (`gcloud run deploy --source=backend`, Google Cloud Buildpacks) -
  added `backend/Procfile` and `backend/.python-version` to control the
  start command and pin the Python version buildpacks previously got
  from the Dockerfile's base image.
- Frontend now builds to `frontend/dist` and is served directly by
  Firebase Hosting; `firebase.json` rewrites only `/api/**` and
  `/video_analysis/**` to the backend instead of rewriting everything.
- Rewrote `scripts/deploy.sh` and `.github/workflows/deploy.yml`: build
  frontend, `gcloud run deploy --source` the backend, `firebase deploy`
  hosting - no more Cloud Build/Docker step, no more `VITE_MAPS_API_KEY`
  build-arg workaround (it's just an env var for `npm run build` now).
- Local dev is now two plain processes (`python backend/main.py` +
  `npm run dev`, Vite proxying `/api` + `/video_analysis` to Flask) -
  updated `frontend/vite.config.ts`'s proxy, `README.md`, and
  `CLAUDE.md` accordingly. Also dropped `.env.sample`'s
  `GCLOUD_ADC_PATH` (was only for the Docker volume mount) and fixed
  `README.md`'s stale AWS-credentials instructions while rewriting that
  section.
- Marked ADR 0001 superseded by new ADR 0004; updated `docs/backlog.md`
  and `docs/runbook.md` to match.

## Live-tested end to end (same session, after pushing the above)

Pushed to `main` and iterated against the real `vietrochack-lab` deploy
until `/video_analysis/analyze_videos` genuinely worked - not just
responded, an actual successful Gemini analysis of a real TikTok URL.
Four real, distinct problems surfaced and got fixed, in order:

1. **Cloud Run's Buildpacks builder no longer offers Python 3.11 at
   all** (only 3.13.x/3.14.x) - `backend/.python-version`'s `3.11.x`
   matched nothing. Bumped to `3.13.x`.
2. That surfaced pinned deps without cp313 wheels: `MarkupSafe==2.1.5`
   and `pydantic==2.7.4`/`pydantic_core==2.18.4` (mismatched pair once
   pydantic_core alone got bumped). Installed a real Python 3.13.15 venv
   locally (`winget install Python.Python.3.13`) and ran a full
   dependency-resolved `pip install -r requirements.txt` to get the
   actual compatible versions (`MarkupSafe==3.0.3`,
   `pydantic==2.11.10`/`pydantic_core==2.33.2`) rather than guessing.
3. **The originally-flagged risk - `cv2` needing `libgl1`/`libglib2.0-0`
   under Buildpacks (no Dockerfile to apt-get install them) - turned out
   to NOT be a problem.** Both `cv2.VideoCapture` (frame sampling) and
   `cv2.imencode` (JPEG encoding) work fine in the Buildpacks-built
   image. ADR 0004's known-risk section and `docs/backlog.md`'s
   verification item are resolved as "confirmed working."
4. What actually broke video analysis were two **pre-existing bugs,
   unrelated to Docker removal** (would have failed identically on the
   old single-container deploy), only surfaced now because this was the
   first real end-to-end test against a real video:
   - The `swipeandfly-gemini-api-key` Secret Manager value had a
     trailing `\r\n` baked in (confirmed via `gcloud secrets versions
     access latest | xxd`), corrupting the `Authorization` header and
     making aiohttp refuse to send the request at all
     (`ValueError: Newline or carriage return character detected in
     HTTP status message or header`). Fixed both ends: `.strip()` on
     all three provider API keys in `const.py`, and pushed a clean new
     secret version.
   - `analyze_from_url`'s post-processing unconditionally did
     `data["activities"]`, but the openai/gemini analysis template
     (`openai_analysis_json_template.txt`) only ever returns
     `{content, location}` - "activities" is exclusively a groq-split-
     flow concept. This is the same bug class as `docs/backlog.md`'s
     existing item #1 for `generate_itinerary` (which does
     `analysis["activities"]` too) - see the new backlog item linking
     them. Fixed with `data.get("activities", [])`.

   Diagnosing both required temporarily adding `print()`s alongside the
   existing file-only `logger` calls in `analyze_videos.py` and
   `openai_request.py`, since Cloud Run only captures stdout/stderr and
   this codebase's logging went to files inside the (ephemeral, per-
   instance) container filesystem instead - kept those prints, they're
   generally useful now.

Final verification: `POST /video_analysis/analyze_videos` with a real
TikTok URL returns a real 200 with genuine Gemini-generated
`content`/`location`, not an error. Homepage and `/api/` still 200 too.
One unrelated, non-recurring `Memory limit of 512 MiB exceeded with 514
MiB used` was seen once on an earlier (failing) request - marginal, not
worth chasing right now, noted in the backlog.

## One more round: the actual frontend flow was still broken

Vuong tried swipeandfly.vietrochack.com directly after the above and it
still errored. Turned out `/video_analysis/analyze_videos` (tested above)
isn't what the frontend actually calls end-to-end - `generate_itinerary`
is, and it has the *exact same* `{summary, activities}` vs
`{content, location}` schema mismatch, just in a second, previously-
unfixed call site (`itinerary_routes.py`, backlog item #1). Since the
default provider is "gemini" (ADR 0003), this meant the app's entire
core feature - swipe videos, get an itinerary - was 500ing on every real
request, regardless of anything in this session's Docker work. Fixed
with the same `.get()`-with-fallback pattern. Live-verified the complete
real flow this time:

- `POST /api/itinerary/generate_itinerary?prompt=...&video_urls=...` ->
  `201` with a real itinerary UUID.
- `GET /api/itinerary/get_itinerary?uuid=...&fields=...` -> `200` with a
  genuine 5-activity NYC itinerary, including one activity explicitly
  `inspiredBy` the analyzed TikTok video's content.

Also found (not yet fixed, low-confidence on frontend impact): the same
`get_itinerary` route will `AttributeError` on `fields.split(',')` if
`fields` is omitted, since `request.args.get('fields')` returns `None`,
not `""`, so its `if fields == "":` guard doesn't catch that case. See
backlog.
